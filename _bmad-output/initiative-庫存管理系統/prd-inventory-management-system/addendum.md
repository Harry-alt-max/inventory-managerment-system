# Addendum: 庫存管理系統 PRD

此文件承載**不屬於 PRD 本體**、但下游工作流（架構設計、UX、實作）需要的深度內容：技術選項與其權衡、來源文件的技術段落、以及被明確擱置的技術決定。PRD 只描述「要做什麼」與「怎麼驗收」；技術「怎麼做」在此。

來源：`庫存管理課題.pptx` 第 2～8 張（技術段落）。PRD 本文對應的是第 10～14 張（業務需求）。

## A. 架構模式：MVVM vs MVC（簡報第 2、3 張）

簡報提出的兩種候選：

| 模式 | 簡報的定位 | 適用判準（依簡報敘述） |
| --- | --- | --- |
| **MVVM**（Model–View–ViewModel） | 複雜的軟體程式、App，強調畫面 UI/UX 優先 | 核心目標是將 UI 與業務邏輯／資料模型徹底分離 |
| **MVC**（Model–View–Controller） | 控制優先的 IoT 專案（輕量化） | 常見的模型－視圖－控制器分工 |

**對本專案的意義**：本系統後台有四種角色、四組高度不同的操作畫面（入庫／領用／移位、採購查詢、銷售組合下單、唯讀查核），畫面邏輯與資料操作分離的價值高於 IoT 情境的輕量化诉求。→ **傾向 MVVM**，但此為架構階段的輸入，最終由 `bmad-architecture` 依實際需求定案。

## C. 憑證與密碼處理（簡報第 4、5 張 + 專案既有做法）

簡報的做法：把資料庫密碼寫在純文字檔中，交給 AI 讀取後連線，而非直接把密碼交給 AI。

**本專案已採用的既有做法（更嚴謹）**：密碼存於 `C:\Users\user\Desktop\pgpass.conf`，格式 `localhost:5432:*:postgres:<password>`，由環境變數 `PGPASSFILE` 指定，密碼不進入任何程式碼、文件或版控。

**對 PRD 的影響（已反映於 FR-1 與 §4.6）**：明文密碼不得出現於程式碼與文件；PRD 只描述「憑證由外部機制提供」。簡報第 4、5 張中的明文密碼值**未被寫入 PRD 與本文件**。

## D. 資料庫邊界原則（簡報第 6 張）

簡報明列的原則：**一個專案一個 DataBase、一個 DataBase 可以有數個表**。

對本專案的意義：
- 既有環境中的 `AILearn` 資料庫即為本專案專用（與課堂流程一致），實作時所有資料表、序列與連線設定集中於此，不與其他專案共用表。
- 「一庫多表」意味著商品、庫存、庫存異動、批次、供應商、銷貨單等實體以**外鍵關聯**共存於同一 schema，而非各自獨立資料庫。
- 權限隔離（登入帳號、角色、操作紀錄）亦落在同一資料庫內，由應用層控管（見 PRD FR-1～FR-3、FR-20）。
- 具體 schema 設計（含外鍵、索引、唯一性約束）由 `bmad-architecture` 定案。

補充（簡報第 6 張的「刪除」說明）：簡報提到刪除可「將其標記為刪除狀態」（軟刪除）。→ **僅適用於設定類資料**（例如已停用的供應商、已下架商品）；**交易類資料（庫存異動、銷貨紀錄、批次）一律不刪除、不軟刪除**，僅追加或反向沖銷（對應 PRD FR-6、FR-19）。

## E. 資料庫設計流程（簡報第 8 張）

簡報指定的作業流程：
1. 由 AI 新建資料庫（`AILearn`）。
2. 以文字檔方式提供憑證給 AI 連線開鎖。
3. 使用 **dbdiagram.io**（類似 Markdown 的圖像式資料庫設計 App）產出 ER 圖，再交由 AI 產出 DDL 與應用程式。
4. 後續由 AI 依既有設計文件迭代。

→ 這是**實作流程**（含 DDL 產生與 ER 設計工具選用），屬於架構與實作階段，PRD 僅在 FR-4、FR-6、FR-9、FR-11 等處隱含「資料模型需支援批次、成本與異動追溯」。
